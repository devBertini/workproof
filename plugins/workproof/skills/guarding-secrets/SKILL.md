# Guarding secrets

If `${user_config.secret_guard}` is false, this module is off: ignore this skill.

Two hooks inspect calls before they run: one every Bash and PowerShell command, one every Read, Grep, Edit and NotebookEdit call. They block the ones that would read or print a secret. A block is the guard working, not an error to route around.

## What it blocks

- A command that is handed the name of a credential file: `.env` and `.env.*` (not `.env.example`, `.env.sample`, `.env.template`), private keys (`id_rsa` and its siblings, `*.pem`, `*.key`, `*.p12`, `*.pfx`, `*.p8`), keystores, cloud and tool credential files (`~/.aws/credentials`, `~/.docker/config.json`, `~/.kube/config`, `.npmrc`, `.pypirc`, `.netrc`, `.git-credentials`, and similar), service-account and OAuth client files, and any pattern the user added in the plugin options.
- The file tools on such a file: `Read`, `Edit` and `NotebookEdit` of it, and a `Grep` whose path is the file or whose glob picks such files (`.env*`, `**/*.pem`).
- Interpreter code that names such a file: `python -c "open('.env')"`, a heredoc fed to `python` or `node`, `bash -c '...'`, `powershell -Command '...'`, `cmd /c '...'`, also behind `docker exec` or `sudo`. A script that only mentions the name (to edit a text file that contains it) is blocked too: write that script to a file with the Write tool and run the file.
- A listed name piped into a reader: `find . -name .env | xargs cat`.
- A command `ssh` runs on a remote host, judged like a local one: `ssh host "cat /srv/app/.env"`.
- Printing the environment: bare `env`, `printenv`, `export -p` or `set`, `Get-ChildItem env:`, `/proc/*/environ`, and printing a variable whose name says it is secret (`echo $API_TOKEN`, `$env:GITHUB_TOKEN`).
- Docker commands that print secrets: `docker compose config` (or `convert`) without `--no-interpolate` or with `--environment`, `docker inspect` or `docker service inspect` without a `--format` that leaves out the environment (`--format json` prints everything), and `env`, `printenv`, `/proc/*/environ` or `cat /run/secrets/...` run inside a container, also behind `sh -c`.

## What stays allowed

Listing, testing, hashing or counting a file (`ls`, `test -f`, `stat`, `wc -l`, `sha256sum`, `git check-ignore`, `git status`, the Glob tool), creating, writing or removing it (the Write tool on a new file, `touch`, `rm`, `> .env`, `>> .env`, `tee .env`, `Set-Content`, `cat > .env <<'EOF'`, `cp .env.example .env`), handing it to the tool that uses it (`docker compose --env-file .env up`, `node --env-file=.env`, `ssh -i ~/.ssh/id_ed25519`), searching for its name (`grep -n .env .gitignore`), naming it in a commit message, `git rm --cached`, using a secret variable without printing it (`curl -H "Authorization: Bearer $API_TOKEN"`), and every call that does not name a secret file.

Searching inside a secret file is reading it and is blocked, even a count or a quiet match (`grep -c '^DATABASE_URL=' .env`, `grep -q`, `Select-String`, the Grep tool): do not plan such a check. To learn whether a key is set, run the program that loads the file and read its own startup or connection error, or ask the user.

## How to proceed

1. Refer to a secret by its path, never by its value. Say "the token in `~/.config/tool/credentials`", do not open it.
2. Let the tool that needs the secret read it: pass the env file to Docker with `--env-file`, give the CLI its config path, run the program that loads the file itself.
3. Never print, copy, echo or paste a secret into a command, a file, a commit message or the conversation. If a task needs a value you cannot see, ask the user to supply it through the tool.
4. To change a secret file without reading it: append a line from the shell (`echo 'KEY=value' >> .env`), or ask the user to make the edit. An existing line cannot be edited blind.
5. For Docker, use `docker compose config --no-interpolate`, `docker inspect --format '{{.State.Status}}' <name>` (a format that does not touch `Config`), and `docker logs`. Secrets a system needs are generated by its own script into an ignored folder and never read back.
6. If a block looks wrong because the file holds no secret, ask the user. Do not rename the file, build the name from pieces or use another program to get around the guard.

## Committing

Use `guarded-commit <repo> "<message>" <path>...`. It stages exactly the paths given and commits them, and it refuses (non-zero exit, reason on stderr, nothing committed, nothing left staged) when a staged file name matches a secret file name or the staged content matches a known token format (GitHub, AWS, Slack, Stripe, Anthropic, OpenAI, Hugging Face tokens, private key blocks). The report names the file, line and kind, never the value. It refuses when something else is already staged. It does not push and it imposes no message style unless the project turned its commit rules on.

If it refuses, remove the secret from the file (read it from the environment instead), add the file to `.gitignore` if it should never be committed, and run it again.

## Limits

The guard matches patterns in commands and file names. It protects against mistakes, not against a command built to hide what it touches, and it is not a sandbox. A Grep over a folder is not blocked and can show a line of a secret file in it: give such a search a glob of the source files you mean.
